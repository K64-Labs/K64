# K64 v0.3.28 - Ring-3 Service Gate

This release adds an explicit Ring-3 gate for non-kernel services. Kernel mechanisms remain registered as kernel services, but every system/root/user service now carries Ring-3 hosting metadata, a required Ring-3 entry image, and a startup verification step. Service command and service-call dispatch refuse non-kernel owners that have not passed that Ring-3 gate.

`servicectl list` now reports the execution boundary for each service as `ring0`, `ring3`, or `blocked`, making isolation state visible at runtime instead of relying on documentation. K64 also ships a tiny `/ex/servicehost.elf` Ring-3 host probe used by built-in services until service-specific Ring-3 hosts are available.

This is a security hardening release, not a completed microkernel conversion. The current process model still lacks a persistent message-driven Ring-3 service server, so service-specific command logic remains kernel-mediated after the Ring-3 gate. The new rule prevents silent non-kernel service startup without a Ring-3 image and creates the enforcement point needed for the next migration step.

v0.3.29 tightens this further by moving `fs`, `proc`, `io`, `sched`, `term`, and `svc` out of the kernel-class service identity set, leaving only the literal `kernel` service as Ring 0 in `servicectl list`.
